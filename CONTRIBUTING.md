# Contributing Guide

How to set up, code, test, review, and release contributions to OregonVR.

## Code of Conduct

Treat teammates respectfully, provide constructive feedback, communicate blockers early, and protect confidential project information. Report concerns to the project manager or instructor.

## Getting Started

Clone the repository:

```bash
git clone https://github.com/swath1p/OregonVR.git
cd OregonVR
```

Follow the setup instructions in `README.md` (still have to add). The team will document the technology stack, dependencies, and commands once they are established. 

## Branching & Workflow

Use `main` as the default branch. Create a descriptive branch for each task. Submit changes through a pull request rather than pushing directly to `main`. Rebase your own branch when needed to incorporate recent changes.

## Issues & Planning

Use GitHub Issues or the team project board to track tasks and bugs. Each task should have a description, acceptance criteria, and an assigned owner. 
## Commit Messages

Use clear messages in the format `type: description`.

Reference the related issue when applicable.

## Code Style, Linting & Formatting

Write readable, consistent, and maintainable code. The team will document the chosen formatter, linter, configuration files, and commands once the technology stack is established.

## Testing

Test new features and bug fixes before submitting a pull request. Add automated tests when appropriate. The team will document its test framework, commands, and coverage requirements during Sprint 2.

## Definition of Done

A contribution is complete when:

- It meets the task's acceptance criteria.
- Relevant tests and configured quality checks pass.
- At least one teammate reviews and approves the pull request.
- Relevant documentation is updated.
- Required CI checks pass before merging.
- No known critical security or confidentiality issues remain.

Checks that are not yet implemented must have an assigned owner and target sprint.

## Contribution Norm

Every contributor must land at least one piece of accepted work per sprint. 
## Pull Requests & Reviews

Pull requests must describe the change, reference the related task when applicable, and report testing performed. Reviewers should check correctness, readability, testing, documentation, and security. At least one teammate must approve before merging.

## Documentation Expectations

Update `README.md` and relevant project documentation when setup instructions, features, or technical decisions change. Keep comments clear and document important assumptions.

## Support & Contact

Ask project questions through microsoft teams. Contact the repository maintainer for GitHub questions and the project manager or instructor for unresolved blockers.
